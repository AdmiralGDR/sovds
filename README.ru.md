# Sovereign Router Brain

[🇬🇧 English](README.md) | 🇷🇺 Русский

Этот репозиторий содержит две чётко разделённые вещи:

1. **[`sovds` — Sovereign Dataset Toolkit](crates/sovds/README.ru.md)** —
   **доменно-агностичная, без единой внешней зависимости, `no_std`**
   библиотека для сбора размеченных датасетов с ground-truth-метками из живых
   систем (безопасная контролируемая инъекция сбоев + телеметрия → эпизоды →
   метрики детекции и безопасности отката). Это переиспользуемый продукт —
   встраивается в любой проект через один трейт. См. её
   [README](crates/sovds/README.ru.md) и
   [пример `host_monitor`](crates/sovds/examples/host_monitor.rs).
2. **Sovereign Router Brain** — **эталонная реализация**: супервизор для
   домашней сети, работающий вне роутера, построенный на `sovds`. Роутер
   остаётся простым и надёжным; вся логика — оценка здоровья, классификация
   сбоев, самолечение — живёт здесь, на машине с реальными вычислительными
   ресурсами (сегодня — ноутбук, позже — домашний сервер). До роутера
   дотягивается только через изолированные адаптеры по SSH.

Оба построены строго по внутренним инженерным принципам проекта (Принципы 0–V, ниже) и,
с 2026-08-08, по его IP-Shield-дополнению. См.
[`docs/SECURITY-POSTURE.md`](docs/SECURITY-POSTURE.md) — что принято,
что осознанно нет, и почему.

## Почему вне роутера

Роутер (MediaTek MT7981, двухъядерный Cortex-A53, ~256 МБ ОЗУ, без NPU) может
тянуть надёжный движок правил, но не полноценную аналитику или LLM. Поэтому
архитектура чётко разделена: крошечное решающее **ядро** без внешних
зависимостей, которое может работать где угодно, и **адаптеры**, которые
берут на себя весь ввод-вывод. То же ядро масштабируется от сегодняшнего
опроса через shell до ML/LLM-ассистированного мозга на домашнем сервере — без
переписывания.

## Архитектура (гексагональная / порты и адаптеры)

```
            ┌─────────────────────────────────────────┐
            │              app (composition root)      │  ← собирает всё, крутит цикл
            │   ┌───────────────────────────────────┐  │
   SSH  ───►│   │   adapters (мосты ввода-вывода)    │  │◄─── ntfy
  роутер    │   │   telemetry · actuator · notifier  │  │     уведомления
            │   └──────────────┬────────────────────┘  │
            │                  │ реализуют               │
            │            ports (трейты)  ← контракты      │
            │                  │ используются               │
            │   ┌──────────────▼────────────────────┐    │
            │   │  core (RouterDomain поверх sovds)  │    │
            │   │  domain · failure · fsm::decide    │    │
            │   └──────────────┬────────────────────┘    │
            │                  │ реализует sovds::Domain   │
            │   ┌──────────────▼────────────────────┐    │
            │   │  sovds (продукт — доменно-агностичен) │ │
            │   │  record · episode · injection ·    │    │
            │   │  dataset · recorder · readiness    │    │
            │   └───────────────────────────────────┘    │
            └─────────────────────────────────────────────┘
```

- **`crates/sovds`** — переиспользуемый продукт-тулкит. `#![no_std]` ядро, ноль
  зависимостей, `std`-фича для файловых частей. См. отдельный README.
- **`crates/core`** — реализация `sovds::Domain` для роутера (`RouterDomain`) +
  чистое решающее ядро: `fsm::decide(state, telemetry, cfg, now)` — тотальная,
  детерминированная, безпаничная функция из наблюдения в действие.
- **`crates/adapters`** — SSH-телеметрия и актуатор, ntfy-уведомления, дренаж
  резервного буфера роутера. Единственный код, которому разрешено касаться
  сети, диска или часов.
- **`crates/app`** — корень композиции и все CLI-инструменты (ниже).
- **`crates/sovml`** — собственное, без единой внешней зависимости, целочисленное
  дерево решений (интерпретируемое, `no_std+alloc`), обучаемое на корпусе `sovds`.

## Решающее ядро в одном абзаце

На каждом цикле телеметрия схлопывается в один самый срочный `FailureClass`
(WAN → процесс → путь → DNS, по каузальной глубине). Дальше конечный автомат
применяет **гистерезис** (никогда не реагировать на один всплеск — сбой должен
подтвердиться N циклов подряд), **эскалацию** (подниматься по фиксированной,
конечной лестнице средств, от наименее разрушительного: смена узла → рестарт
→ перезапуск WAN → фейловер → перезагрузка) и **cooldown с backoff** (никогда
не дёргаться туда-сюда). Восстановление признаётся немедленно на любом шаге.

## Как это соотносится с инженерными принципами проекта

| Принципа | Где живёт в коде |
|---|---|
| 0 · Код — пассив | Каждый generic-механизм живёт один раз в `sovds`; роутер поставляет только свой домен. |
| I · Агностичное ядро | `core`/`sovds` — `no_std`; весь ввод-вывод инъецируется через трейты `ports`. |
| I · Карантин зависимостей | Ноль сторонних крейтов во всём workspace. |
| II · Невозможность невалидных состояний | Подсистемы — перечисления, а не булевый суп; `State` — алгебраический тип; `Source`/диагностированный сбой/метка инъекции никогда не спутать. |
| II · Ноль глобального состояния | `decide` берёт состояние + конфиг явно; никаких статиков. |
| II · ACID / откат | `Actuator` возвращает `Ok` только после проверки постусловия. |
| III · Проверка на этапе компиляции | `#![forbid(unsafe_code)]`; clippy запрещает unwrap/panic/индексацию/переполнение. |
| III · Ограниченное исполнение | Фиксированный массив узлов; конечная лестница эскалации; насыщающая арифметика. |
| III · Изящная деградация | Показания `Unknown` никогда не запускают действие; сбой уведомления не фатален; проверки целостности алертят, никогда не самоуничтожаются. |
| III · Никакой паники | Ошибки — значения `Result`; нигде нет `unwrap`/`expect`/`panic`. |
| IV · Оправданная оптимизация | Сейчас Rust; Zig-агент на роутере — только когда профилирование это потребует. |
| V · Воспроизводимые сборки | `rust-toolchain.toml` + `Cargo.lock` фиксируют всё; `scripts/reproducible-build.sh` сам себя проверяет на побайтовую идентичность. |
| V · Нулевая терпимость CI/CD | CI: `fmt --check` + `clippy -D warnings` + `test`, всё блокирующее. |
| IP Shield | AGPL-3.0-or-later, подписанные коммиты, `SHA256SUMS` + OpenTimestamps. См. [документ о защите IP](docs/SECURITY-POSTURE.md). |

## Сборка и проверка

```sh
cargo fmt --all --check                      # форматирование не обсуждается
cargo clippy --all-targets --locked -- -D warnings   # предупреждения = ошибки
cargo test --workspace --locked              # детерминированные unit-тесты
sh scripts/reproducible-build.sh --print     # Принципа V: все бинарники побайтово идентичны
sh scripts/verify-integrity.sh               # установленные бинарники совпадают с SHA256SUMS
```

## Инструменты

10 CLI-бинарников, все собираются `cargo build --release --locked`:

- `sovereign` — живой супервизор (только наблюдение, пока не задан `SOVEREIGN_ACTUATE`).
- `sovereign-inspect [log]` — метрики датасета (баланс классов, распределение задержек).
- `sovereign-episodes [log] [--list]` — сегментирует лог на **эпизоды сбоев**
  (реальная единица обучения/анализа) и печатает готовность к обучению по классам.
- `sovereign-inject <class> [--secs N]` — включает **метку ground-truth-инъекции**.
- `sovereign-export [log] [out.tsv]` — разворачивает датасет в TSV-таблицу признаков.
- `sovereign-anomaly [log] [--top N]` — **unsupervised**-скан кандидатов на пробелы в правилах.
- `sovereign-train [log] [--depth N]` — обучает интерпретируемое дерево решений
  (`sovml`) на корпусе, оценивает на отложенной выборке.
- `sovereign-replay` — переигрывает корпус с другими адаптивными настройками.
- `sovereign-backfill` — дренаж без потерь резервного буфера роутера.
- `sovereign-scenario` — переигрывает канонический набор сценариев сбоев через
  живой решающий конвейер; единственный способ измерить редкие классы
  (`wan_down`, `singbox_dead`, `dns_fail`), которых пассивному сбору всегда мало.

См. [`FORMAT.md`](FORMAT.md) (формат записи) и
[`deploy/README.ru.md`](deploy/README.ru.md) (установка с нуля).
